## How to read an item

Each item says how sure it is:

- **[R]** reproduced in the main review session, by running the tool or a browser.
- **[A]** reproduced by a reviewing agent with the command shown; not run a second time.
- **[C]** reasoned from the code; nobody ran it. Reproduce it before fixing it.

Line numbers are those of commit `ebeb4ae`. `op` stands for `bun <repository>/src/cli.ts`, run in an empty scratch folder outside the repository.

## Rules for every fix

These come from `AGENTS.md` and the technical specification.

1. A fix lands with a test that fails without it. For a control, run the revert once and say so in the commit.
2. A change to what a person can do updates `docs/product-spec.md`; a change to how updates `docs/tech-spec.md`; both in the same commit, with a CHANGELOG line.
3. After a change to a rule, a command, a flag, a setting, or a name: `bun src/cli.ts guide --reference > docs/reference.md` and `bun tools/tech-spec.ts`.
4. After a change under `viewer/`: `bun run build:viewer`, and commit `assets/viewer.html` and `assets/viewer.css`.
5. A recorded result changes only on purpose: `RECORD=1 bun test tests/cases.test.ts`, and list each changed result in the commit.
6. Never weaken the allow-list, the policy, the sandbox, the `</template` count, or the path rule to pass a test.
7. `bun run check` before a change lands, one full suite at a time.
